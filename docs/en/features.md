# ✨ Features

* 📝 **Single Structured Form:** The teacher fills in one syllabus plan — course description, objectives, contents, methodology, references, grading criteria — instead of three separate, easily-diverging documents (internal plan, student-facing plan, tutor plan).
* 💾 **Per-Field Autosave:** Every narrative field saves on its own via a debounced web service call, with a "saving…/saved" indicator, so a long form never risks losing work — the same pattern already proven in `mod_reflect`.
* 🧩 **Dynamic Weeks & Activities:** Weeks and, inside each week, activities are added, edited and removed on the fly through web services (upsert with `id = 0` for a new record), with duration in hours, type/category, dates and points.
* 🗂️ **Narrative Content via Custom Fields API:** Ementa, objectives, contents, methodology, per-week details, references, grading criteria, interaction tools, tutoring follow-up and notes are all `core_customfield` fields across three areas (`plan`, `week`, `activity`), pre-seeded on install and manageable per-institution from **Site administration**.
* ✍️ **Lazy-Loaded Rich Text:** Narrative fields activate the Tiny editor only on focus, instead of loading it for every field up front — keeping a long form's edit mode responsive.
* 🔄 **Plan Approval Workflow:** A state machine — `draft` → `submitted` → `approved` / `changes_requested` — gates the activity's own visibility: the course module stays hidden until coordination approves it, and reappears with the last approved content if changes are requested again after a first approval.
* 🔁 **Hybrid Post-Approval Editing:** Once approved, narrative content stays freely editable without reopening review; changing a structural field (a week's title/duration/period, or an activity's type/category/dates/points) immediately regresses the plan to `submitted`, flagging a pending review to coordination without hiding the activity or reverting content already visible to students and tutors.
* 🚫 **Self-Approval Guard:** A user cannot approve or request changes on a plan they submitted themselves, even when they hold the review capability.
* 🗒️ **Per-Field Coordinator Notes:** Beyond the single free-text justification used when requesting changes, coordination can attach, edit or clear a note on any specific narrative field — plan, week or activity — right below that field, in the same read view they already use to review the plan; the note box is exclusive to that read-only view, so a user who can also edit the plan's content never sees it duplicated there. Notes survive a resubmission and are cleared automatically once the plan is next approved.
* ✉️ **Resubmission Note:** When resubmitting after changes were requested, the teacher can leave an optional note back to coordination explaining what changed — shown on the plan page while the review is pending and included in the reviewer's notification, cleared the same way as the coordinator note above once the plan is approved.
* 👥 **Three Role-Based Views:** The same stored data renders three tabs from a single source — the full plan (coordination/teacher, with submit/review actions), the tutor plan (with grading criteria and answer keys), and the student plan (without answer keys or tutoring follow-up notes).
* 📊 **Consolidated Schedule:** An activities-and-grading schedule table is computed by aggregating over the plan's own weeks and activities — never a separate table to keep in sync.
* 🔔 **Native Notifications, Sent in the Background:** Submission, approval and changes-requested events notify the right people (coordination on submission; the author on approval or changes requested) through the Message API, no custom delivery channel — queued as a background task so the workflow action itself returns immediately, regardless of how slow the site's mail delivery is.
* 📦 **Backup & Restore:** Full Moodle 2 backup/restore support for the plan, its weeks, activities and Custom Field values, correctly remapped on restore or course duplication.
* 🔐 **Privacy API:** The plan's content is the course's own pedagogical record, not personal data — only the three workflow actor references (submitted/reviewed/unpublished by) are treated as personal data, anonymised rather than deleted so the plan itself survives a data-deletion request.
* 🛡️ **Capability-Gated Roles:** Dedicated capabilities for viewing, submitting, reviewing and viewing the tutor-only view, so coordination, teacher and tutor each see exactly what their role allows.
